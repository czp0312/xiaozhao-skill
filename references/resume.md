# 简历诊断与改写模块

用于校招和实习技术岗简历 review、针对 JD 改写、项目经历优化。

## 诊断顺序

1. 明确目标公司、目标岗位和 JD。
2. 检查基础资格：毕业时间、学历、专业、城市、实习时长。
3. 检查结构完整性：教育、技能、项目、实习、获奖、开源等。
4. 检查岗位技能匹配。
5. 检查项目相关度和个人贡献。
6. 检查结果表达：规模、指标、用户、质量、效率、成本。
7. 检查可信度风险和过度包装。
8. 给出按优先级排序的修改建议。

## 问题优先级

```text
P0：硬伤，会直接影响筛选或存在诚信风险。
P1：强影响问题，目标岗位匹配度明显下降。
P2：中影响问题，表达不够有竞争力。
P3：低影响问题，格式、措辞、细节优化。
```

## 常见问题

- 只写“参与、负责、熟悉、优化”，没有具体动作。
- 技能栈堆砌，但项目里没有对应证据。
- 个人贡献不清楚，看不出“你做了什么”。
- 没有结果、规模、难点、用户、质量或效率信号。
- 简历方向和目标岗位不一致。
- 夸大职责、伪造指标、使用无法解释的技术名词。
- 工科背景简历只写机械或硬件本体工作，没有转译出目标岗位要的工程能力。

## 工科转技术岗的表达重点

机械、自动化、电子等背景转技术岗时，重点是把原有经历转译成目标岗位能读懂的证据，而不是隐瞒专业背景。

- 硬件/机械项目要写清“你写的代码或算法在哪一层”：上位机、控制算法、固件、驱动、标定工具、数据处理脚本。
- 控制类项目用指标说话：控制周期、跟踪误差、稳态误差、响应时间、负载能力、测试次数。
- 机器人项目写清软件栈：ROS 版本、仿真环境、传感器、通信方式、你负责的模块。
- 嵌入式项目写清器件与工具链：主控型号、RTOS、总线、调试手段（示波器、逻辑分析仪、J-Link）。
- CV 或图像项目写清数据规模和效果：数据集规模、标注方式、指标（mAP、准确率）、推理耗时。
- 不要用“熟悉 C++”这类无证据表述，改成“用 C++ 实现了什么、达到什么效果”。
- 跨专业不要写成劣势，写成“软硬协同”“整机视角”“真实环境调试经验”这类岗位真正稀缺的能力。

## 改写原则

- 只改表达，不发明事实。
- 不添加用户没提供的指标、工具、职责或结果。
- 缺失数据用 `[真实指标]`、`[请确认]`、`[业务规模]` 等占位。
- 突出个人动作、技术方案、难点权衡和结果。
- 对每一条改写说明为什么这样改。

推荐句式：

```text
背景/目标 + 个人动作 + 技术方案 + 难点/权衡 + 结果
```

## 不同岗位的表达重点

- 前端：组件抽象、状态管理、性能优化、工程化、跨端、可视化、复杂交互。
- 后端：接口设计、数据模型、缓存、消息队列、数据库、稳定性、异常处理。
- AI 应用 / 大模型：业务场景、LLM / RAG / Agent、工具调用、评估、延迟、成本、稳定性。
- 算法 / CV：问题定义、数据、模型、训练、评估、指标、实验。
- 具身智能 / 运控：控制周期、规划算法、仿真与实机差异、传感器融合、故障处理。
- 嵌软 / 嵌硬：主控与器件选型、实时性、总线协议、功耗、可靠性与调试过程。
- IC 设计：模块划分、时序收敛、验证覆盖率、面积与功耗权衡。
- 测试开发：测试体系、自动化框架、覆盖率、缺陷发现、CI。

## 输出模板

诊断：

```text
整体判断：
P0 硬伤：
P1 强影响问题：
P2 中影响问题：
P3 细节优化：
岗位适配建议：
需要补充的信息：
下一步：
```

改写：

```text
改写版本：
修改理由：
需要确认/补充的信息：
不建议这样写的点：
```

多版本改写：

```text
通用版本：
目标公司/JD 定制版本：
差异说明：
```
